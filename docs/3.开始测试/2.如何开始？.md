## 如何开始？

项目确定了是类似知乎的问答类应用，接下来我们面临的问题是：

> 我们该从何开始呢？

---

## MVP 原则

互联网产品开发有一个重要的 `MVP` 原则：

> **MVP（Minimum Viable Product）**：最小化可行产品。指开发团队通过提供最小化可行产品获取用户反馈，并在这个最小化可行产品上持续快速迭代，直到产品到达一个相对稳定的阶段。

### MVP 的核心思想

```
┌─────────────────────────────────────────┐
│                    MVP 开发流程                          │
├─────────────────────────────────────────────────┤
│                                                         │
│   定义核心功能 → 开发 MVP → 获取反馈 → 持续迭代         │
│       ↑                                      │         │
│       └──────────────────────────────────────┘         │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 我们该如何应用 MVP？

首先，我们定义问答类产品最核心的功能是**回答问题**。那么，基础功能包括：

- 发布问题
- 编辑问题
- 回答问题

但是，这些真的是必须要做的吗？**在开发回答问题的功能之前，我们真的有必要先完成发布问题、编辑问题的功能吗？**

为什么我们不能采取**人工导入**的方式来建立问题呢？

### 从运营角度考虑

如果我们是在运营一个产品，在初期我们可以：

- ❌ 不需要提问功能
- ✅ 由运营同事手动发布问题（例如通过向数据库插入数据）
- ✅ 让用户参与到产品当中

这样做还有一个好处：**可以在一开始控制提问的品质**。

## 确定开发优先级

所以我们关注**最核心的功能**：**回答问题**，并假设已经有问题了。

### 功能拆解

围绕「回答问题」这个核心功能，我们进行需求拆分：

```
回答问题
├── 1. 展示问题列表    ← 第一个测试
├── 2. 展示问题详情
├── 3. 回答问题
├── 4. 编辑问题
└── 5. 发布问题（后期补充）
```

### 开发顺序

| 优先级 | 功能 | 说明 |
|--------|------|
| P0 | 展示问题列表 | 用户需要看到有哪些问题 |
| P1 | 展示问题详情 | 用户需要查看问题内容和回答 |
| P2 | 回答问题 | 用户可以发表回答 |
| P3 | 编辑/删除回答 | 用户可以管理自己的回答 |
| P4 | 发布问题 | 后期由运营手动发布过渡到用户自主发布 |

## TDD 开发流程

在开始编写第一个测试之前，我们先了解 TDD 的基本流程：

### 红 - 绿 - 重构循环

```
┌─────────────────────────────────────────────────────────┐
│                   TDD 开发循环                          │
│                                                         │
│    ┌─────────┐     ┌─────────┐     ┌─────────┐        │
│    │  编写   │     │  运行   │     │  重构   │        │
│    │  测试   │ ──→ │  测试   │ ──→ │  代码   │        │
│    │ (失败)  │     │ (通过)  │     │         │        │
│    └─────────┘     └─────────┘     └─────────┘        │
│         ↑              │                              │
│         │              │                              │
│         └──────────────┘                              │
│              编写最少代码                              │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 详细步骤

| 步骤 | 动作 | 说明 |
|------|------|------|
| 1️⃣ | 编写一个测试 | 定义期望的行为 |
| 2️⃣ | 运行测试（失败） | 验证测试有效，看到「红」 |
| 3️⃣ | 编写最少代码 | 使测试通过，看到「绿」 |
| 4️⃣ | 运行测试（通过） | 确认功能正常 |
| 5️⃣ | 重构代码 | 优化代码质量 |
| 6️⃣ | 运行测试（通过） | 确保重构未破坏功能 |
| 7️⃣ | 重复 | 回到步骤 1，继续下一个功能 |

### TDD 的优势

- ✅ 更清晰地思考需求
- ✅ 设计出更松耦合的代码
- ✅ 获得重构的信心（测试保护网）
- ✅ 文档即代码（测试即文档）
